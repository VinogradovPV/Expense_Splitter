## 2. Главная цель

Создать приложение, которое заменяет или дополняет текущий Excel-подход к учету совместных покупок.

8. Формировать минимальный или близкий к минимальному список переводов между участниками.
9. Работать через удобный CLI-интерфейс, пригодный для PowerShell.

### 3.3. Главное правило распределения

Стоимость покупки распределяется **не между всеми участниками системы**, а только между участниками конкретной покупки.

Пример:

- Павел купил кофе на 1200 рублей.
- Покупка относится к группе `кофе`.
- В группе `кофе` 6 участников.
- Доля каждого участника: 1200 / 6 = 200 рублей.
- Павел оплатил 1200 рублей.
- Павел получает положительный баланс +1000 рублей по этой операции.
- Остальные участники группы получают отрицательный баланс -200 рублей каждый.

## 4. Расчет балансов

Для каждой покупки:

1. Взять сумму покупки.
2. Определить список участников покупки.
3. Разделить сумму между участниками покупки.
4. Начислить долю каждому участнику покупки.
5. Добавить полную сумму в `paid` плательщика.
6. Для каждого участника рассчитать:

```text
net = paid - share
```

Где:

- `paid` — сколько участник фактически оплатил;
- `share` — сколько участник должен был оплатить по своей доле;
- `net` — чистый баланс.

Интерпретация:

- `net > 0` — участнику должны вернуть деньги;
- `net < 0` — участник должен перевести деньги другим;
- `net = 0` — участник ничего не должен и ему ничего не должны.

## 5. Минимизация переводов

Итоговый расчет должен выдавать не полный список взаимных задолженностей, а минимизированный список переводов.

Алгоритм:

1. Сформировать список должников: участники с `net < 0`.
2. Сформировать список кредиторов: участники с `net > 0`.
3. Отсортировать должников по модулю долга по убыванию.
4. Отсортировать кредиторов по сумме переплаты по убыванию.
5. Последовательно закрывать долги:
   - взять текущего должника;
   - взять текущего кредитора;
   - сумма перевода равна минимуму из остатка долга и остатка переплаты;
   - уменьшить остаток должника и кредитора;
   - перейти к следующему должнику или кредитору, когда остаток закрыт.
6. Завершить, когда все остатки закрыты в пределах допустимой погрешности округления.

Требования:

- количество переводов должно быть минимальным или близким к минимальному для данной модели;
- алгоритм должен быть детерминированным;
- порядок результатов должен быть стабильным;
- алгоритм должен быть покрыт тестами.

## 6. Деньги и округления

Требования к денежным расчетам:

1. Не использовать `float`.
2. Использовать `Decimal`.
3. Поддержать настройку округления.
4. По умолчанию округлять до рублей.
5. Явно описать правило округления в README.
6. Проверять сценарии, где сумма не делится ровно между участниками.
7. Не терять и не создавать деньги при округлении.

Рекомендуемый подход:

- внутренние расчеты вести с высокой точностью;
- итоговые суммы переводов округлять по единому правилу;
- остатки из-за округления распределять детерминированно, например по алфавиту участников или по порядку в списке.



```python
from_participant: str
```

4. Все участники покупки должны существовать в списке участников.
5. Плательщик может не входить в список участников покупки, если он просто оплатил за других. Это правило нужно явно описать в README и покрыть тестом.

## 19. Ограничения и запреты

Не делай следующее:

1. Не используй `float` для денег.
2. Не помещай всю бизнес-логику в CLI.
3. Не делай один монолитный скрипт.
4. Не хардкодь весь проект только под текущий Excel.
5. Не рассчитывай долги по схеме “каждый каждому”, если можно минимизировать переводы.
6. Не игнорируй округления.
7. Не оставляй код без тестов.
8. Не удаляй существующие файлы без необходимости.
9. Не меняй бизнес-правила молча.
10. Не выводи огромные логи без необходимости.
11. Не трать контекст на рассуждения, которые не помогают завершить проект.
12. Не коммить `.venv`, `__pycache__`, `.pytest_cache`, временные Excel-копии, приватные данные и большие бинарные артефакты без необходимости.
13. Не пушь в `main` напрямую, если можно работать через feature branch.
14. Не выдумывай GitHub URL, токены, права доступа или успешный push.
15. Не скрывай неудачные проверки. Проваленный тест — это не “почти успех”, а маленький пожар с номером строки.
