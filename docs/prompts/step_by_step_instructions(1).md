# Пошаговая инструкция для Manus: реализация проекта учета совместных расходов с GitHub и REPORT.md

## 1. Назначение документа

Этот документ описывает порядок работы Manus agent при создании Python-проекта для учета совместных покупок и распределения расходов.

Основной промпт с бизнес-требованиями находится в отдельном документе: `manus_prompt_expense_splitter.md`.

Используй этот документ как рабочий регламент выполнения задачи. Если основной промпт отвечает на вопрос “что сделать”, этот документ отвечает на вопрос “как именно работать, чтобы не устроить цифровую археологию в репозитории”.

---

## 2. Общий принцип работы

Действуй как автономный coding agent:

1. Сначала анализируй workspace.
2. Затем проверяй Git/GitHub-состояние.
3. Потом формируй короткий план.
4. Создай или обнови `REPORT.md`.
5. Реализуй проект по шагам.
6. После каждого крупного блока обновляй `REPORT.md`.
7. После каждого крупного блока запускай релевантные проверки.
8. Исправляй ошибки сразу.
9. Делай логические Git-коммиты.
10. В конце подготовь push/PR, если GitHub remote доступен.
11. Предоставь короткий финальный отчет.

Не превращай процесс в бесконечное обсуждение. Ценность агента в том, что он делает работу, а не устраивает симпозиум имени очевидных мыслей.

## 3. Экономия токенов и контекста

Manus должен экономить токены и не засорять контекст.

### 3.1. Что делать

1. Перед чтением файлов изучай дерево проекта.
2. Читай только релевантные файлы.
3. Для больших файлов используй поиск по ключевым словам.
4. Сначала смотри имена листов, заголовки и структуру Excel, а не пытайся выводить весь файл.
5. Пиши краткие статусы только после завершения значимых этапов.
6. Финальный отчет делай компактным.
7. Храни промежуточные выводы в `REPORT.md`, а не в длинных сообщениях.
8. Если нужно показать код, показывай только важные фрагменты.
9. Не повторяй бизнес-требования, если они уже заданы в основном промпте.
10. Если появляется ошибка, анализируй минимальный релевантный лог.
11. Для Git используй summary-команды: `git status --short`, `git log --oneline -n 5`, а не огромные дампы истории.
12. В `REPORT.md` фиксируй факты компактно: этап, статус, файлы, решения, проверки.

### 3.2. Чего не делать

1. Не печатай содержимое всех файлов целиком.
2. Не повторяй один и тот же план после каждого шага.
3. Не создавай несколько конкурирующих архитектур.
4. Не объясняй каждую строку кода.
5. Не выводи полный лог тестов, если достаточно summary.
6. Не трать контекст на общие рассуждения о Python, CLI или архитектуре.
7. Не загружай в контекст нерелевантные файлы.
8. Не переписывай README несколько раз без причины.
9. Не генерируй длинные отчеты, если задача требует рабочего кода.
10. Не вставляй в `REPORT.md` полные исходники, большие логи или содержимое Excel целиком.

## 5. Шаг 2 — Проверка Git и GitHub

Проверь состояние контроля версий.

### 5.1. Проверки

Выполни:

```bash
git status --short
```

Если это Git-репозиторий, также выполни:

```bash
git branch --show-current
git remote -v
git log --oneline -n 5
```

Если Git еще не инициализирован, реши, нужно ли выполнить:

```bash
git init
```

### 5.2. Правила безопасности

1. Если есть несохраненные пользовательские изменения, не затирай их.
2. Если есть чужие изменения, зафиксируй это в `REPORT.md`.
3. Не делай `git reset --hard`, `git clean -fd`, force push и rebase без явной необходимости.
4. Не пушь напрямую в `main`, если можно создать feature branch.
5. Не выдумывай GitHub remote.
6. Если remote отсутствует, зафиксируй: `GitHub remote not configured; repository URL required for push`.

### 5.3. Рабочая ветка

Если Git доступен, создай ветку:

```bash
git checkout -b feature/expense-splitter-core
```

Если ветка уже существует, используй ее или создай новую, например:

```bash
git checkout -b feature/expense-splitter-core-2
```

Обнови `REPORT.md`: текущая ветка, remote, состояние workspace.

## 11. Шаг 8 — Расчет балансов

Реализуй расчет:

1. На входе:
   - участники;
   - покупки;
   - настройки округления.
2. На выходе:
   - список `Balance`.

Логика:

1. Инициализировать `paid = 0`, `share = 0` для каждого участника.
2. Для каждой покупки добавить сумму покупки плательщику в `paid`.
3. Разделить сумму между участниками покупки.
4. Добавить долю каждому участнику покупки в `share`.
5. Рассчитать `net = paid - share`.

Добавь тесты:

1. одна покупка на всех;
2. покупка на подгруппу;
3. несколько покупок;
4. неравное деление;
5. участник без покупок;
6. плательщик вне участников покупки.

После шага:

```bash
python -m pytest tests/test_calculator.py
```

Обнови `REPORT.md` и сделай коммит:

```bash
git add .
git commit -m "feat: add balance calculation"
```

## 16. Шаг 13 — GitHub Actions CI

Если проект использует GitHub, добавь `.github/workflows/ci.yml`.

Минимальный CI:

1. Checkout репозитория.
2. Setup Python 3.11 или 3.12.
3. Установка зависимостей.
4. Запуск `pytest`.
5. Запуск `ruff check .`, если ruff настроен.

Пример состава workflow:

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - name: Install package
        run: python -m pip install -e .[dev]
      - name: Run tests
        run: python -m pytest
      - name: Run ruff
        run: python -m ruff check .
```

Если dev extras не настроены, адаптируй установку зависимостей.

После шага обнови `REPORT.md` и сделай коммит:

```bash
git add .
git commit -m "ci: add GitHub Actions workflow"
```

## 21. Правило остановки

Остановись, когда выполнены критерии:

1. Код создан.
2. CLI работает хотя бы по основному сценарию.
3. Балансы считаются.
4. Переводы минимизируются.
5. Тесты расчетов проходят.
6. README создан.
7. `REPORT.md` создан и обновлен по этапам.
8. Git-ветка и коммиты созданы, если Git доступен.
9. GitHub push/PR выполнены или честно зафиксирована причина невозможности.
10. Финальный отчет предоставлен.

Не продолжай улучшать косметику, если основная задача выполнена.
